# Provenance of the context-manifest simulation sets

Written 2 Oct 2026, lane L4, tracking issue #1505. Read this before you read any number from a set.

## What a clean hold-out means here

The discipline is the one sets A to D of engine v1 followed, and it is written down because set D was spent: a set a builder has read results on, to tune a rule, is a development set from that moment, whatever it was called when it was made.

1. The ground truth of a set is generated by `scripts/gen_context_set.py`, written to `data/groundtruth_context_<SET>.jsonl`, and its SHA-256 is recorded in `data/groundtruth_context_hashes.json`. Both are committed before any emitter call. The emitters check the hash first and refuse to run on a file that does not match.
2. Scoring reads that file and never Provy's output to decide what was injected.
3. A hold-out is read once. `scripts/score_context.py` keeps a ledger of reads (`data/holdout_reads.jsonl`), refuses a second read without `--allow-reread`, and stamps a reread result "NOT CLEAN".
4. Nobody, including the builder of a rule, looks at Provy's findings for a hold-out before the bars are checked. If a bar is missed, the miss is written up as a finding. A threshold is not moved to fit the set, because that turns a rule into a rule about one fleet.

### The one regeneration, before any emission

The four CM sets were committed once (`4a16b105`, hashes `31ce8bdf...`, `6dca8098...`, `5d91a6b0...`, `d18343f8...`) and regenerated once, in the commit that follows it. No request had been sent to Provy and no Provy output existed. The emitter tests, run against a fake server that follows SPEC 4.4, showed that a fleet-declared field map binds its line to the agent's `decision` event, and for an agent whose deciding step is an `agent_message` to that agent's first event, which is the retrieval step. A fault planted on such a step would be judged on the wrong step by the spec's own rule. The generator now plants faults and decoys on the map route only on agents whose deciding step is a `decision`. CAP-B did not change. CAP-A was regenerated once more, in the capture unit, before any emission, to add 9 clean sessions that send no manifest and 5 that send items with no as_of date, so the Context card has a headline below 100%, a dates line below the headline, and a gap to show (its first hash was `b2e16071...`). The CM sets did not change in that step, and a test checks that the generator still produces the committed bytes. Nothing of Provy's was read for any set at any point, so the hold-outs stay clean. The earlier hashes are listed here so the history can be checked. A hold-out is not regenerated after its first emission.

## Arithmetic: why the sets are this size

A hold-out fleet runs 180 sessions. A fault fleet plants 6 stale, 6 unapproved, 4 empty and 3 instruction changes, which is 19 faults. CM-B has four fault fleets (76), CM-C and CM-D have three (57 each). The brief asks for at least 40 injected faults per hold-out. Every one is above it.

Clean sessions, meaning no fault and no decoy: 579 in CM-B, and the other two are in the same range (the scorer prints the exact count). A false alarm bar of 5% on about 580 clean sessions is 29 sessions. A build with no false alarm at all has a 95% upper bound of about 3 in 580, half a percent, so zero false alarms and a 5% rate are far apart on this set.

Per kind in CM-B: stale 24, unapproved 24, empty 16, instruction changes 12. The recall bar (over 60%) is read over the 64 stale, unapproved and empty faults together, and over the ones that settled badly (about 70% of them) for the cause-naming half. The instruction bar (over 90% detected) rests on 12 changes in CM-B and 30 across the three hold-outs, which is small, and the scorer prints the count beside the percentage.

## Why faults sit after a warmup

The two learned checks need history. `retrieval_empty` wants at least 20 other recorded retrievals on a step. `instructions_changed` wants a hash on two earlier sessions. Every fault is planted at session 40 or later, so a miss is Provy's and not a missing sample. Empties are at most 2.2% of any step's retrievals in the fault fleets, so the learner's own 95% line is not crossed by the plan.

## Decoys: things that look like faults and are not

| Decoy | What it is | Where it can sit |
|---|---|---|
| `at_limit` | a fact exactly at the fleet's limit. The check is "older than", so it passes | routes whose recorded time is exact (not the log door, whose times come from a model) |
| `stale_unused` | an old fact the agent retrieved and set aside (`used: false`) | routes that can carry `used` |
| `unapproved_unused` | an unlisted source, set aside | routes that can carry `used` |
| `input_old` | an old item of kind `input`: the request itself has no age to judge | routes that carry every kind |
| `oi_empty_unknown` | an OpenInference retriever span with no documents and nothing saying zero. Unknown, not empty | the convention fleet only |
| `quiet_empty` | an empty retrieval on a fleet that is empty about 6% of the time by design | the CM-D quiet fleet only |
| `case_source` | an approved source spelled in a different case | any route. See the conflict below |
| standing A/B | one agent alternates between two instruction versions from the start | the CM-D quiet fleet. Its first six sessions are excluded from every bar |

There is no quiet-day decoy in the fault fleets, on purpose. An empty retrieval on a step that is non-empty 98% of the time cannot be told from the fault by anything but the base rate, so planting one there would be planting a fault and calling it a decoy. The quiet-day case lives in a fleet whose base rate makes it quiet.

## Where this lane departs from the spec or the brief, so nobody finds it by surprise

1. **CM-C and CM-D carry faults.** The spec (12.4) says CM-C has no levers and CM-D raises nothing. The brief for this lane asks for at least 40 injected faults in every hold-out. Both are met: three of the four fleets in CM-C and CM-D carry faults, and the fourth is the spec's role (one fleet with no fault, one quiet-day fleet). The false alarm rate is still read over sessions with no fault, and the scorer splits it by fleet role.
2. **The case-variant decoy is a spec conflict.** SPEC 6.1 says `allowed` entries match a source exactly, which is case sensitive, so `Policy-KB` is not on a list that says `policy-kb`. The brief calls it a decoy. The ground truth follows the brief (no finding expected) and marks those sessions `bar_excluded: case_source_spec_conflict`. They are in no bar. The scorer reports what Provy did with them on a separate line. If the lead rules that matching is case insensitive, nothing changes in the files. If the ruling is exact match, those sessions become faults and the set is a new set, because a hold-out is not edited.
3. **`post_change_first_repeat`.** The session after an instruction change, on a route that carries the instruction, is excluded from the bars. SPEC 6.3 says a hash is known after two earlier sessions and fails once on a hash never carried, so the second session carrying the new hash is ambiguous. From the third session on it is a plain clean session.
4. **Routes are finer than doors.** The ground truth names six routes: `rest`, `sdk`, `otlp_native`, `otlp_convention` (an OpenInference retriever span and a GenAI instruction attribute together), `log_line` (the whole-line JSON form and the key-value form) and `log_map` (a fleet-declared field map). Provy's own per-door coverage is four doors, and the plan records both.
5. **A fault is planted only where its route can carry it.** A route that cannot express a fault would produce a recall miss that is the simulator's. The map is `ROUTE_CAPS` in `engine/context.py` and a test pins it.
6. **The log door's second form is a stand-in for a model.** The log door sends lines to a model that writes the events. The simulator emits plain JSON event lines and the context line beside them. What the model makes of the event lines is not testable here.

## What this simulation cannot show

It measures a fleet the builders made. The 11 Sep 2026 lesson in CLAUDE.md applies in full: a rule measured at 100% on the simulator would have selected almost nothing on production. No production fleet sends any context today. A pass here says the checks do what the spec says on fleets built to the spec. It says nothing about how real agents use `used`, `as_of` or `retrieval.returned`.

## 3 Oct 2026 (L10): the declared rows changed, the ground truth did not

`config/context_sets.py` changed in one place only: `DECLARATIONS["guardrails"]` (and the two capture lists built from it) went from two rows that selected `step_type: decision` to six rows, one freshness and one approved-list row per agent, each selecting by agent and naming no step type, so a run exercises the product's default of reading the decision steps (`decision` and `agent_message`). The generator, the data files and their SHA-256 hashes were NOT touched: `data/groundtruth_context_*.jsonl` and `data/groundtruth_context_hashes.json` are byte for byte what they were, `tests/test_context_declarations_default.py` re-verifies every recorded hash, and nothing in `engine/` reads the declarations. One recorded field goes stale and is left alone on purpose: each set's `generator_sha256["config/context_sets.py"]` in the hash file is the hash of the file as it was when the set was generated. It is a record of the file at that moment, nothing checks it, and rewriting it would be rewriting a sealed record. No hold-out was read or emitted again for this change.
